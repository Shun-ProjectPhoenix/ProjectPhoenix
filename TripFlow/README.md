## TripFlowとは

TripFlowは、出張に関する予約情報を一つにまとめ、

- 何を予約済みか
- 何がまだ不足しているか
- 費用はいくらか

をすぐ確認できる出張管理アプリです。単なる出張記録ではなく、**「出張に必要な予約がそろっているかを3秒で確認できること」**を中心的な価値としています。

Gmailに届いた予約メールを検索・解析し、確認したうえでTripFlowへ登録できる機能も備えています（詳細は[Gmail連携](#gmail連携検索からtripflowへの本登録まで)を参照）。

---

## 開発背景・解決したい課題

出張の予約情報は、Gmail・えきねっと・スマートEX・航空会社・ホテル予約サイト・電話予約・Googleカレンダーなど、複数のサービスに分散しがちです。そのため出張前に「予約が揃っているか」を確認するだけで、いくつものサービスを開き直す必要があります。

TripFlowは、これらの情報を一つの画面にまとめることで、出張が多い方・予約メールを探すのに時間がかかる方・予約漏れを防ぎたい方の負担を減らすことを目指しています。

## 「v1.0」の意味について

このREADME・`docs/`配下で扱う「v1.0」は、**開発者本人が日常的に安心して使えるローカル／開発環境版としての完成**を指します。具体的には、出張・予約管理とGmail連携が実機で問題なく動作し、ユーザー分離やエラー処理が安全に作り込まれている状態です。

`docs/roadmap.md`には、これとは別に、クラウドDBへの移行・独自ドメイン・利用規約・プライバシーポリシー整備・一般公開といった**不特定多数のユーザーへ公開するSaaS化**を指す記述があります。これは今回のv1.0とは別のマイルストーンであり、混同しないよう`docs/roadmap.md`側でも節を分けて整理しています。

## Googleログイン・ユーザーごとのデータ分離

TripFlowにGoogleアカウントでのログインを導入し、利用者ごとにデータを分離しています。

### ログイン・ログアウト

- Streamlitのネイティブ認証機能（`st.login()` / `st.logout()` / `st.user`）を利用し、Googleアカウントでログインできます
- 未ログイン状態では、出張・予約・カレンダーなどTripFlow本体の画面は一切表示されず、ログイン画面のみが表示されます
- ログイン後はヘッダーに「ようこそ、〇〇さん」と表示名（取得できない場合はメールアドレス）が表示され、「ログアウト」ボタンからいつでもログアウトできます
- ログアウト時は、TripFlow内部で使っているセレクトボックスの選択状態・削除確認フラグ・カレンダーの選択日などの一時的な状態（session_state）をすべてクリアしてからログアウト処理を行います

### ユーザーごとのデータ分離

- Googleアカウントごとに`users`テーブルへ1件登録され、以後すべての出張・予約はそのユーザーに紐づけて保存されます
- ユーザーの識別には、変更される可能性があるメールアドレスではなく、Googleが発行する不変の識別子（`sub`）を使用しています
- 出張データは`user_id`で所有者を管理し、予約データは出張（`trip_id`）経由で所有者を判定します（`reservations`テーブル自体にはuser_id列を持たせない設計）
- 出張・予約の取得・更新・削除は、すべてログイン中のユーザーIDによる絞り込み・所有者チェックを経由します。他のユーザーの出張IDや予約IDを直接指定しても、閲覧・編集・削除は一切できません。**これはGmail経由で登録した予約（後述）についても同様で、Gmail由来だからといって所有者チェックを迂回する経路はありません**
- 万一、セレクトボックスの状態に存在しない、または他人のIDが残っていても、安全に未選択状態へ戻り、アプリがクラッシュしたり他人のデータが表示されたりすることはありません
- 他ユーザーのTrip/Reservationへアクセスできないことは、自動テストでも回帰的に確認しています（`web/tests/test_database.py`の`UserIsolationRegressionTests`）

### 既存データ（Web v0.2以前）の扱い

- Web v0.2以前（ログイン機能が無かった時代）に登録されたデータは、`legacy user`という特別な内部ユーザーに割り当てられた状態で保持されています
- 実際にご自身のGoogleアカウントでログインできることを確認したうえで、`legacy user`のデータをそのアカウントへ移行する作業を別途行います（データの削除は行いません）

## 出張・予約管理の基本機能

### ホーム画面

- 今月の費用（`status=予約済み`の予約金額のみを集計。キャンセル済みの予約は除外）
- 今月の出張予定件数（月をまたぐ出張も重複なく1件としてカウント）
- 今月の予約件数
- 確認が必要な出張件数（今月の出張のうち、予約漏れがあるもの）
- 上記4項目はそれぞれ開閉式（`st.expander`）の内訳表示に対応し、タップ／クリックで詳細を確認可能
- 直近の出張（最大3件）を開閉式カードで表示し、行き先・予約漏れ状況・その出張の予約一覧を確認可能
- 出張タブへの詳細導線：「出張予定」「予約」「確認が必要」「直近の出張」の各項目に「詳細へ」ボタンがあり、押すと出張タブ側で該当の出張（予約から押した場合はその予約も）が自動的に選択された状態になります。Streamlitの仕様上タブの自動切り替えはできないため、出張タブを開くと選択済みの状態が確認できる形です
- 出張ごとの予約状況判定（`get_reservation_status()`）は、DB読み取りに失敗した場合でも「予約完了」等の正常状態として誤って扱わず、安全側（未確認扱い）にフォールバックしたうえで、他のDB読み取り処理と同じ日本語エラーメッセージを表示します

### 出張管理

- 出張の新規登録（出張名・行き先・開始日・終了日・分類［業務／プライベート／未分類］・メモ）
- 入力チェック（出張名必須、終了日は開始日以降）
- 出張一覧表示（予約状況列つき）
- 出張の編集・削除（削除は確認ステップあり）

### 予約管理

- 予約の新規登録・編集・削除（対象は編集・削除ともにセレクトボックスで明確に指定）
- 項目：種類（往路／ホテル／復路／その他）、サービス（えきねっと／スマートEX／スカイマーク／Agoda／その他）、予約名、利用日（またはホテルのチェックイン・チェックアウト日）、金額、予約番号、予約確認URL、状態（予約済み／未予約／キャンセル）、メモ
- 出張とのひもづけ（`ON DELETE CASCADE`により、出張削除時に関連予約も自動削除）
- 削除前に種類・サービス・予約名・日付（または宿泊期間）・金額を表示する確認ステップあり
- 予約確認URLはhttp/https以外のスキーム（`javascript:`など）をリンクとして表示しない安全対策つき

### 予約詳細カード

出張タブの各予約を、項目ごとに開閉できるカード形式で確認できます。

- 種類・サービス・予約名・利用日（ホテルはチェックイン日／チェックアウト日）・金額・予約番号・予約確認URL・状態・メモを、「項目名」を上、「値」を下に積んだ形式で表示（スマホでも文字が詰まらないレイアウト）
- 値が未入力の項目は「なし」、ホテルのチェックアウト日が未設定の場合は「未設定」と表示
- 予約確認URLが安全なリンク（http/https）の場合のみ「予約確認ページを開く」ボタンを表示
- 状態に応じたバッジ（✅予約済み／⚠️未予約／🚫キャンセル）を表示
- 従来の一覧表（`st.dataframe`）は「予約一覧（表）」として引き続き利用可能

### 予約漏れチェック

- 出張ごとに「往路」「ホテル」「復路」それぞれに`status=予約済み`の予約が存在するかを自動判定
- 3つとも揃っていれば「予約完了」、1つでも不足していれば「確認が必要」と表示
- `未予約`・`キャンセル`の予約は完了扱いにしない

### カレンダー

- 月間カレンダー表示（前月・翌月への移動、今日の日付をハイライト）
- 出張期間を黒系のバーで表示（複数日にまたがる出張・月をまたぐ出張にも対応）
- 予約をサービスごとに色分け表示（詳細は次項）
- キャンセル済みの予約は取り消し線、未予約の予約は破線枠で区別
- 日付を選択すると、その日に関係する出張・予約の詳細を画面下部に表示
  - 「🧳 出張」「🚄 往路」「🏨 ホテル」「🚄 復路」「📌 その他予約」ごとにグループ化されたカード形式で表示（予約詳細カードと同じ形式）
  - ホテル予約は選択した日が「🟢 チェックイン」「🔵 宿泊中」「🟠 チェックアウト」のどの段階かをバッジで表示
- 月表示グリッドは、スマホ幅（390px／375px／360pxで確認済み）でも横スクロールなしで日〜土の7列すべてが画面内に収まるようにレスポンシブ対応（PC幅では従来どおりのグリッド幅・余白を維持）

### ホテルのチェックイン・チェックアウト対応

- ホテル予約のみ、チェックイン日・チェックアウト日を個別に入力（チェックアウト日はチェックイン日より後である必要あり）
- カレンダー上では宿泊期間全体を表示し、日ごとに「チェックイン」「宿泊中」「チェックアウト」を区別して表示
- 既存データ（チェックイン日のみ記録されていた予約）は、安全なマイグレーションにより自動的に「チェックイン日＝利用日」として移行済み（チェックアウト日は推測せずNULLのまま）

### 予約サービス別の色分け

カレンダー上で、予約サービスごとに色分けして表示します。

| サービス | 色 |
|---|---|
| 出張期間 | 黒系 |
| えきねっと | 緑系 |
| スマートEX | 水色系 |
| スカイマーク | 黄色系 |
| Agoda | 赤系 |
| その他 | グレー系 |

### スマートフォン対応

PC向けのレイアウト（`layout="wide"`、横並びカラム、カレンダーグリッド構造）を維持したまま、狭い画面幅でも主要操作が行えるように調整しています。

- カレンダーの月表示グリッドは、スマホ幅で横スクロールなしに7列すべてが画面内に収まる（詳細は上記カレンダー参照）
- 予約詳細カード・日付詳細カードは、項目を「ラベル→値」の縦積みで表示し、狭い画面でも文字が詰まらない
- ホーム画面の各項目の「詳細へ」ボタン、出張登録・予約登録フォームの日付2カラム（開始日／終了日、チェックイン日／チェックアウト日）などは、Streamlitの`st.columns`が持つ画面幅に応じた自動縦積みの挙動を利用しており、狭い画面では自然に縦並びになる
- ボタンの最小高さ・フォントサイズを調整し、タップしやすくしている
- 実機（スマートフォン）でカレンダー・予約カード・ホームの導線ボタンの表示を確認済み

## Gmail連携：検索からTripFlowへの本登録まで

**Gmailの予約メールは自動では登録されません。** 検索・分類・解析はすべてユーザー操作で行い、内容を確認したうえで「TripFlowに登録」ボタンを押した場合にのみDBへ保存されます。

### 対応サービス

現在、以下4サービスの予約メールに正式対応しています。

| サービス | 種別 |
|---|---|
| えきねっと | 電車（新幹線） |
| スマートEX | 電車（新幹線） |
| スカイマーク | 飛行機 |
| Agoda | ホテル |

各サービスとも実際のメールを使った複数回の実機確認を経て解析ロジックを調整していますが、**各サービスのメール文面・レイアウトが変更された場合、解析に失敗したり、一部項目が取得できなくなったりする可能性があります**（既知の制限として後述）。全てのメール形式・全ての文面パターンでの動作を保証するものではありません。

### 全体の流れ

1. **Gmail検索**：出張タブ内の「📧 Gmailから予約を探す」から、対象サービス（1サービスまたは「すべて」）・検索期間（1／3／6／12ヶ月）を指定して検索
2. **メール分類**：検索結果の各メールを、件名・送信元から自動分類（詳細は次項）
3. **本文解析**：「予約情報を解析」ボタンを押した1件についてのみ、メール本文を取得して項目を抽出
4. **予約候補プレビュー**：抽出できた項目（日付・区間・時刻・列車名／便名・号車・座席・ホテル名・チェックイン／アウト・料金・予約番号等）をカード形式で表示。取得できなかった項目があれば明示します
5. **予約日とTrip期間の照合**：抽出した予約日（交通は乗車日、ホテルはチェックイン日）が期間に含まれる出張だけを、登録先の候補として絞り込みます
6. **登録先Trip確認**：候補の出張が1件も無ければ登録UI自体を表示せず、「先に出張を登録してください」と案内します。候補がある場合はセレクトボックスで選択（無関係な出張は選択肢に出ません）
7. **予約種別確認**：交通の場合は往路／復路／その他をユーザー自身が選択します（日付からの自動判定は行いません）。ホテルは種別を「ホテル」に固定します
8. **登録内容確認**：登録先出張・予約種別・タイトル・区間・時刻・金額・予約番号等、実際に保存される内容を表示します
9. **ユーザーが「TripFlowに登録」を押す**：ここで初めてDBへの保存（`INSERT`）が行われます。ボタンを押すまでは一切DBに書き込まれません
10. **DB保存**：`source_type='gmail'`・`gmail_message_id`・`gmail_thread_id`とともに保存されます
11. **ホーム／カレンダー反映**：保存後は、他の予約と同様にホーム画面・カレンダー・予約詳細に反映されます

### メール分類

検索で見つかったメールは、件名・送信元をもとに次の4種類に分類されます。

| 分類 | 意味 | 解析 | 登録 |
|---|---|---|---|
| 🟢 予約情報抽出対象（TARGET） | 予約内容がひとまとまり含まれる、最も情報が揃ったメール | 可 | 可 |
| 🔵 予約補完メール（SUPPLEMENTARY） | 座席番号案内など、単独でも一部情報を含む関連メール | 可 | 不可（手動で解析結果を確認することは可能） |
| 🟡 判定不能（UNKNOWN） | TARGET/SUPPLEMENTARY/EXCLUDEDのいずれにも機械的に分類できないメール | 可 | 不可 |
| ⚪ 対象外（EXCLUDED） | 案内・レビュー依頼など、予約情報を含まないと判断したメール | 不可 | 不可 |

TripFlowへ登録できるのはTARGETに分類されたメールのみです。同一予約について複数のメール（購入完了メール・座席指定メール等）が届く場合がありますが、**これらを自動で1件に統合する処理は現時点では行っていません**（既知の制限を参照）。

### 予約解析で取得できる情報

サービス・メールの内容によって取得できる項目は異なりますが、対応しているのは主に以下です。

- 日付（乗車日／搭乗日）
- 区間（出発地→到着地）
- 出発／到着時刻
- 列車名（えきねっと・スマートEX）
- 便名（スカイマーク）
- 号車・座席番号
- ホテル名（Agoda）
- チェックイン日・チェックアウト日（Agoda）
- 料金（メールに金額の記載がある場合のみ）
- 予約／申込番号

**メールに存在しない値を推測で補うことはしません。** 取得できなかった項目は登録候補プレビュー上で「取得できなかった項目」として明示されます。

### 二重登録防止

同じGmailメール（`gmail_message_id`が同一）から2回以上TripFlowへ登録することを防止しています。

- DB側の`gmail_message_id`照合を永続的な正本とし、ログアウト・ブラウザ更新・アプリ再起動・別セッションをまたいでも「登録済み」と判定されます
- 画面表示のタイミングに加えて、「TripFlowに登録」ボタンが押された直後・実際にDBへ保存する直前にも再度照合し、二重クリックや複数タブ操作による競合を防ぎます
- session_stateによる同一セッション内の判定は、上記DB照合を毎回省略しないための補助として引き続き使用しています
- 判定は必ず現在ログイン中のユーザーの予約に限定されます。他ユーザーが同じメール（別アカウント）を取り込んでいても、それによって現在ユーザーの登録がブロックされることはありません

**この仕組みが防ぐのは「同じメールからの2回登録」のみです。** 同一予約について送られてくる別メール（購入完了メールと座席指定メールなど）は`gmail_message_id`が異なるため同一予約とは判定されません。また、同じ内容を手動でもう一度登録した場合の重複も防げません（既知の制限を参照）。

### 予約日とTrip期間の自動マッチング

Gmail解析結果の予約日を使って、その日付を含む出張だけを登録先の候補にします。

- 交通（電車・飛行機）は解析した乗車日／搭乗日、ホテルはチェックイン日を基準日とします
- `trip.start_date <= 基準日 <= trip.end_date` を満たす出張だけが選択肢に表示され、無関係な出張は選択できません
- 該当する出張が無い場合は登録UI自体を表示せず、「この予約日を含む出張が登録されていません。先に出張を登録してください」と案内します
- 基準日を取得できなかった場合（日付の解析に失敗した場合）も、誤登録防止のため登録UIを表示しません

現時点では、ホテルの`checkout_date`が出張の終了日を超える場合などの、より詳細な整合性チェックは行っていません（既知の制限を参照）。

### 個人情報・秘匿情報の扱い

- Gmailのaccess tokenは、その場のAPI呼び出しにのみ使用し、DB保存・ログ出力・画面表示は一切行いません（`refresh_token`も取得・保存していません）
- メール本文全文はDBに保存しません。DBに保存されるのは、解析済みの日付・区間・列車名／便名・号車・座席番号・金額・予約番号・`gmail_message_id`／`gmail_thread_id`などの構造化された情報のみです
- 氏名・会員番号・電話番号・住所などの個人情報は、解析結果（登録候補）にも一切含めない設計です

## コード構成の改善の記録

機能面の変更ではありませんが、以下のコード構成の改善を行ってきました。

- **表示ロジックの共通化**：出張・予約の表示に関する定数・整形関数・カード表示コンポーネント（`render_reservation_card`、`render_trip_card`など）を`web/components.py`に切り出し、ホーム／出張／カレンダーの各画面で重複していた表示コードを共通化しました
- **DB読み取り時のエラー処理**：書き込み（登録・更新・削除）だけでなく、読み取り処理（`safe_fetch()`）にも`sqlite3.Error`のハンドリングを追加し、DBの読み込みに失敗した場合でも画面全体がクラッシュせず、エラーメッセージを表示したうえで空データ等の安全な値として継続表示するようにしました。出張ごとの予約状況判定（`get_reservation_status()`）も同じパターンで保護しています
- **所有者チェック付きCRUD**：`database.py`の出張・予約に関する全関数がログインユーザーのIDを必須で受け取り、取得・更新・削除の際にSQL文中で所有者条件を確認するようになりました。更新・削除は影響行数（0件なら「対象が存在しないか権限が無い」）を返す設計です。これらは自動テストでも回帰的に確認しています
- **session_stateの安全なクリア**：`clear_stale_selection()`を新設し、削除やユーザー切り替えなどでセレクトボックスの選択状態に無効なIDが残っても、アプリがクラッシュせず安全に未選択状態へ戻るようにしました

## Googleログインの設定（開発環境）

Googleログインが必須のため、起動前に以下の設定が必要です。

1. Google Cloud ConsoleでOAuthクライアントID（ウェブアプリケーション）を作成し、承認済みのリダイレクトURIに `http://localhost:8501/oauth2callback` を登録します
2. Gmail連携（検索・解析・登録）を使う場合は、OAuth同意画面でGmail読み取り専用スコープ（`gmail.readonly`）を有効にしてください
3. リポジトリのルート（`TripFlow/`。`web/`配下ではありません）に `.streamlit/secrets.toml` を作成し、`client_id` / `client_secret` / ランダムな `cookie_secret` を設定します

   ```toml
   [auth]
   redirect_uri = "http://localhost:8501/oauth2callback"
   cookie_secret = "（ランダムな文字列）"
   client_id = "（Google Cloud Consoleで発行されたクライアントID）"
   client_secret = "（同、クライアントシークレット）"
   server_metadata_url = "https://accounts.google.com/.well-known/openid-configuration"
   ```

   上記はすべてプレースホルダです。実際の値は各自のGoogle Cloud Console設定に置き換えてください。

4. `.streamlit/secrets.toml`は`.gitignore`で除外されており、GitHubにはコミットされません。**実際の値を直接コードやドキュメントに記載しないでください**

Streamlitは、`streamlit run`を実行したときの**作業ディレクトリ**基準で`.streamlit/secrets.toml`を探します。TripFlowは通常リポジトリルートを作業ディレクトリとして起動するため、配置場所を`web/`配下にしないよう注意してください。

## 既知の制限事項

- **Gmail連携関連**
  - 対応しているのはえきねっと・スマートEX・スカイマーク・Agodaの4サービスです。各サービスのメール文面・レイアウトが変更された場合、解析に失敗したり一部項目が取得できなくなったりする可能性があります
  - 同一予約について届く複数メールを自動で1件に統合する処理は未実装です（それぞれ別メールとして扱われます）
  - SUPPLEMENTARYメール（座席案内等）の内容を、対応するTARGETメールの登録内容へ自動的に補完・統合する処理は未実装です
  - `gmail_message_id`による二重登録防止は「同じメールから2回登録すること」だけを防ぎます。同じ内容を手動でもう一度登録した場合の重複は防げません
  - メールが再送され`message_id`が変わった場合の類似判定は未実装です
  - 予約変更・キャンセルメールが届いても、TripFlow側のstatusへ自動反映されません（手動で状態を更新する運用が必要です）
  - 金額の記載が無いメールの場合、0円として保存されます（実際に無料という意味ではなく「取得できなかった」ことを表しています）
  - ホテルの`checkout_date`が出張の終了日を超える場合など、より詳細な日程整合性チェックは未実装です
  - 区間・時刻・列車名／便名・号車・座席番号などの一部詳細情報は、専用のDB列ではなく予約名（title）・メモ（memo）へ変換して保存しています
- **その他**
  - 1つのGoogleアカウントにつき1ユーザーとして扱う想定で、複数アカウントの同時連携には対応していません
  - データは起動している端末のローカルSQLiteファイルに保存され、複数端末間の同期はできません
  - カレンダーはバーを直接クリックする方式ではなく、日付を選択して詳細を確認する方式です
  - 金額は円単位の整数のみ対応しています
  - 予約確認URLはhttp／https以外のスキームをリンクとして表示しません（スキームなしの入力は自動的に`https://`を補完します）
  - 出張・予約の検索／絞り込み機能はまだありません
  - ホームの「詳細へ」ボタンを押しても、Streamlitの仕様上タブは自動的に切り替わりません（出張タブを開くと選択済みの状態になります）
  - 管理者画面は無く、ユーザーの一覧確認・削除等はできません
  - クラウドDB移行・一般公開等の公開SaaS化は、今回のv1.0（ローカル版）とは別マイルストーンです（「v1.0の意味について」を参照）
