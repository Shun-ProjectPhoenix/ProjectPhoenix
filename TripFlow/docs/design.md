# TripFlow 設計書

## 1. プロジェクト名

TripFlow

---

## 2. コンセプト

TripFlowは、出張に関する予約情報を一つにまとめ、

「何を予約済みか」
「何がまだ不足しているか」
「費用はいくらか」

をすぐ確認できる出張管理アプリです。

TripFlowの中心的な価値は、単なる出張記録ではなく、

> 出張に必要な予約がそろっているかを3秒で確認できること

です。

---

## 3. 想定ユーザー

- 出張が多い会社員
- 新幹線、飛行機、ホテルを別々のサービスで予約する人
- 予約メールを探すのに時間がかかる人
- 出張費用をまとめて確認したい人
- 予約漏れを防ぎたい人

---

## 4. 解決したい課題

現在、出張の予約情報は次のようなサービスに分散しています。

- Gmail
- えきねっと
- スマートEX
- 航空会社
- ホテル予約サイト
- 電話予約
- Googleカレンダー

そのため、出張前に予約状況を確認する際、複数のサービスを開く必要があります。

TripFlowでは、これらの情報を一つの画面にまとめます。

## 8. Gmail取り込みの設計原則

Gmailから取得した情報は、自動では登録しません。

処理の流れ：

1. Gmailから予約候補を取得
2. 抽出結果を確認画面に表示
3. ユーザーが内容を確認
4. 必要に応じて修正
5. 登録ボタンを押して保存

以下の処理は禁止します。

- 確認なしの自動登録
- キャンセル予約の物理削除
- プライベート予約の自動削除
- 出張への強制的な自動紐づけ

自動判定は、あくまで候補の提案に留めます。

Web v0.4 Phase Bの実機確認により、上記「1. Gmailから予約候補を取得」の前段として、
「そのメールが予約情報抽出の対象として適切かどうかを判定するフィルタリング」が
別途必要であることが判明した。詳細は13.3を参照。

## 12. Web v0.3の認証・ユーザー分離設計

### 12.1 認証方式

- **Streamlitのネイティブ認証機能**（`st.login()` / `st.logout()` / `st.user`）を採用。自前でOAuthフローを実装していない
- プロバイダは**Google（OIDC）**の1つのみ。複数プロバイダ・複数アカウントの同時連携は行わない
- 認証設定（`client_id` / `client_secret` / `cookie_secret` / `redirect_uri` / `server_metadata_url`）は`.streamlit/secrets.toml`に保持する
- リダイレクトURIは`{アプリのURL}/oauth2callback`固定。ローカル開発では`http://localhost:8501/oauth2callback`

### 12.2 usersテーブルとユーザー識別

- `users`テーブルを新設し、Googleアカウントごとに1件のユーザー行を持つ（7.0節参照）
- ユーザー識別子には、Googleが発行する**不変の`sub`（google_sub列）**を使用する
- メールアドレス（email列）はGoogle Workspace等の設定変更で変わり得るため、識別キーとしては使わず、表示・連絡用の付随情報として保持するにとどめる
- ログイン成功のたびに`google_sub`でユーザーを検索し、無ければ新規作成、あれば`email`/`display_name`を最新の値に更新する（`get_or_create_user`）

### 12.3 所有者管理とCRUD時の所有者チェック

- `trips`テーブルに`user_id`列を追加し、出張の所有者を直接管理する
- `reservations`テーブルには`user_id`を**持たせない**。予約の所有者は常に`reservations.trip_id → trips.user_id`の経路のみで判定する（reservationsとtripsの2箇所に所有者情報を持たせると、同期がズレた場合に他人のデータが見える事故につながるため、所有者情報は1箇所に一本化する設計とした）
- 出張・予約の取得・更新・削除は、すべてSQL文中のWHERE句で所有者条件（`user_id = ?`、または`trip_id IN (SELECT id FROM trips WHERE user_id = ?)`）を伴う
- 更新・削除は影響行数（0件／1件）を返す設計とし、0件の場合はアプリ側で「対象データが見つからないか、操作する権限がありません」という共通メッセージを表示する（対象が存在しないのか、他人の所有物なのかは区別して表示しない）
- 予約の新規登録時は、対象の`trip_id`がログインユーザーの所有物であることを事前に確認し、そうでなければ例外（`OwnershipError`）を送出する
- user_idは常にGoogleの認証情報（`st.user.sub`）から特定したものだけを使用し、画面からの入力やsession_stateの値だけを信用して決定することはしない

### 12.4 session_stateの安全性

- ログアウト時は、TripFlow固有のsession_state（出張・予約の選択ID、ホームからのジャンプ先、削除確認フラグ、カレンダーの選択日など）をすべてクリアしてから`st.logout()`を呼ぶ
- 削除やユーザー切り替え等により、セレクトボックスのsession_stateに存在しない、または他ユーザーのIDが残った場合でも、アプリがクラッシュしたり他人のデータが見えたりしないよう、有効なID一覧に無い値は事前にクリアする（`clear_stale_selection`）

### 12.5 legacy userの扱い

- Web v0.2以前（ユーザー概念が無かった時代）のデータは、`google_sub = 'legacy-local-data'`のプレースホルダーユーザー（legacy user）に割り当てて保持する
- 特定のGoogleアカウントへの自動割り当ては行わない（複数アカウントでの開発・テスト時に、意図しないアカウントへ既存データが渡ってしまう事故を避けるため）
- 実際のご本人のGoogleアカウントでログインできることを確認したうえで、legacy userのデータをそのアカウントへ移行する（`trips.user_id`の付け替えのみ。データの削除は行わない）

### 12.6 secrets.tomlの役割

- `.streamlit/secrets.toml`に、Google OAuthのクライアント情報・Cookie署名用の秘密文字列を保持する
- Streamlitは`streamlit run`実行時の**作業ディレクトリ**基準で`.streamlit/secrets.toml`を探すため、TripFlowではリポジトリルート（`web/`配下ではない）に配置する
- `.gitignore`で除外し、GitHubにはコミットしない
- Gmail APIのトークン（アクセストークン・リフレッシュトークン）は、Web v0.3時点ではSQLiteに保存していない（Gmail連携が未実装のため不要。将来Gmail連携を実装する際に、保存方法を別途設計する）

## 13. Web v0.4 Phase A・Bの実装内容

### 13.1 認証方式

- Web v0.4 Phase Aでは、既存のGoogleログイン（`st.login()`、12章参照）のOAuthスコープを拡張し、Gmail読み取り専用スコープ（`https://www.googleapis.com/auth/gmail.readonly`）を追加した
- アクセストークンはStreamlitの`expose_tokens`設定により`st.user.tokens.access`から取得する。refresh_tokenは取得・保存しない（`st.user`経由では取得できない仕様のため）。アクセストークンが失効した場合は、ユーザーに再ログインを促す案内を表示する
- 独立したOAuthフロー・refresh_tokenの永続化は行わない（案A採用）。将来的にバックグラウンド同期等の要件が生じた場合に、案B（独立OAuthフロー、refresh_token保存）への移行を検討する

### 13.2 Gmail検索

- `web/gmail_service.py`を新設し、既存依存のhttpxでGmail REST API（`users.messages.list`・`users.messages.get`）を直接呼び出す構成とした（新規ライブラリは追加していない）
- 検索はサービス（えきねっと／Agoda）ごとに、送信元ドメイン・件名キーワードをORで束ねたqパラメータと、期間条件（`after:`）を組み合わせて実行する
- 1サービスあたり最大20件、ページングなし（全メールの無制限走査はしない）
- 取得する情報は件名・送信元・受信日時・snippet（Gmailが生成する短い抜粋）のみで、メール本文（`payload.body`）は取得しない

### 13.3 Phase Bの実機確認で判明した課題（Phase Cへの引き継ぎ）

実際のGmail環境で検索したところ、以下が判明した。

- **えきねっと**：予約確認メール以外に、出発前案内・座席番号案内など、同じ旅行に関連する複数種類のメールが検索候補に含まれる
- **Agoda**：予約確認メール以外に、宿泊後のレビュー依頼メール等も検索候補に含まれる

このため、Phase Cで本文解析を実装する際は、8章の「登録前にユーザーが確認する」という原則に加えて、
**「そのメールが予約情報抽出の対象として適切かどうかを判定するフィルタリング」を解析の前段に設ける必要がある**
ことが分かった。この判定ロジックの設計（キーワードベースか、件名パターンベースか等）は、Phase Cで改めて検討する。

### 13.4 セキュリティ

- アクセストークンはDB・session_stateいずれにも保存しない。API呼び出しの都度、その場でのみ使用する
- 検索結果（候補一覧）はsession_stateに一時保持するが、メール本文全文は含めない。ログアウト時は既存の`session_state.clear()`でまとめて破棄される
- Gmail API呼び出しは常にログイン中ユーザー自身のアクセストークンを使うため、他ユーザーのメールにはアクセスできない

## 14. Web v0.4 Phase Cの実装内容（メール判定・抽出・登録候補表示）

Phase Cのゴールは「Gmail → 自動でDB登録」ではなく、**登録候補をユーザーが確認できるところまで**。
DBへのINSERTは行わない（8章の原則を維持）。

### 14.1 メール分類（フィルタリング）

`web/reservation_parser.py`に分類ロジックを新設した。

- 分類は4段階：`予約情報抽出対象` / `予約補完メール` / `対象外` / `判定不能`（`予約補完メール`はPhase C実機確認1回目を受けて追加。14.8参照）
- 判定は**件名のキーワードマッチのみ**で行い、本文取得前に完了する（対象外と判定したメールは本文を取得しない）
- サービスごとに、より限定的なルール（例：えきねっとの`予約補完メール`）→「対象外キーワード」→「対象キーワード」の順で評価し、どれにも一致しなければ`判定不能`とする
- キーワードは、ユーザーが実際にGmail環境で確認したメール種別カテゴリをもとにした初期案であり、実際の件名文言をすべて確認し尽くしたものではない。キーワードテーブル（`SUBJECT_CLASSIFICATION_RULES`）を編集するだけで調整できる構造にしてあり、13章「実メール確認」で継続して見直す前提

### 14.2 Gmail本文取得

`web/gmail_service.py`に`fetch_message_body()`を追加した。

- 「予約情報抽出対象」または「判定不能」と判定され、かつユーザーが「予約情報を解析」ボタンを押した1件についてのみ、Gmail APIを`format=full`で呼び出す（候補一覧全件への自動呼び出しはしない）
- `payload.parts`を再帰的にたどり、multipart/alternative・multipart/mixed等ネストした構造からtext/plainとtext/htmlを収集する。添付ファイル（`attachmentId`のみを持つパート）は無視する
- text/plainを優先し、無ければtext/htmlを`reservation_parser.html_to_text()`（正規表現ベースの簡易変換）でテキスト化する

### 14.3 抽出項目

- **えきねっと**：乗車日・出発時刻・到着時刻・出発駅・到着駅・列車名・号車・座席番号・申込/予約番号
- **Agoda**：ホテル名・チェックイン日・チェックアウト日・予約ID・料金
- いずれも正規表現ベースのルールで、メールに存在しない項目は`None`のまま扱い、推測で補完しない
- AI（OpenAI API等）による解析はPhase Cでは使用しない（9章の方針どおり）

### 14.4 登録候補データ構造

`reservation_parser.ReservationCandidate`（dataclass）として保持する。フィールドは`service` / `message_id` / `relevance` / `reservation_type`（電車・ホテル・その他） / `confidence`（高・中・低） / `title` / `date` / `start_time` / `end_time` / `origin` / `destination` / `train_name` / `car_number` / `seat_number` / `hotel_name` / `checkin_date` / `checkout_date` / `amount` / `reservation_reference` / `missing_fields`。

`confidence`は、抽出できた項目数の単純カウントではなく「予約として重要な項目」の充足度で判定する（Phase C実機確認1回目でのユーザーからの指摘を反映。14.8参照）。えきねっとは乗車日・区間（出発駅+到着駅）・列車名・出発/到着時刻の4項目、Agodaはホテル名・チェックイン日・チェックアウト日の3項目を基準とし、すべて揃えば「高」、2項目以上揃えば「中」、それ未満は「低」とする（`_confidence_from_core`）。

現行の`reservations`テーブル（7.2節）とは1対1で対応しない（`train_name`・`car_number`・`seat_number`等、現行スキーマに無い項目を含む）。この構造はプレビュー表示専用であり、DBへは一切保存しない。reservationsテーブルへの保存方法・スキーマ拡張（`gmail_message_id`列の追加を含む）はPhase Dで検討する。

### 14.5 UI

「📧 Gmailから予約を探す」の候補一覧の各カードに、以下を追加した。

- 分類バッジ（🟢予約情報抽出対象／⚪対象外／🟡判定不能）
- 対象外以外に「🔍 予約情報を解析」ボタン（押した1件のみ本文取得・解析を実行）
- 解析結果を、種類（電車／ホテル）に応じたレイアウトの登録候補プレビューカードとして表示（`components.render_registration_candidate_card`）。値が存在しない項目は表示しない
- 「登録」ボタンはPhase Cでは実装しない（Phase Dへ）。プレビューカードには「登録機能は今後のバージョンで実装予定」である旨を常に表示し、8章の「ユーザーが確認してから登録する」原則を維持する

### 14.6 個人情報・秘匿情報の扱い

- 抽出対象は14.3節の項目のみ。氏名・会員番号・電話番号・住所は抽出ロジックの対象にしていない
- 本文全文・access tokenはsession_stateに保存しない。session_stateに保持するのは抽出済みの構造化データ（`ReservationCandidate`）とエラーメッセージ文字列のみ
- テストfixtureには実際のメール本文を一切含めない（人工的なサンプルのみ使用）

### 14.7 既知の制限・今後の課題

- 分類・抽出ルールはいずれも実際のメール件名・本文を確認せずに設計した初期案であり、実機確認（`docs/roadmap.md`参照）での調整が前提
- 重複登録防止（`gmail_message_id`によるチェック）はPhase D以降。`ReservationCandidate.message_id`をそのまま将来の`gmail_message_id`列に転用できる想定
- キャンセル・変更メールの検知はWeb v0.5（design.md 6章）以降で対応

### 14.8 Phase C実機確認（1回目）を踏まえた解析精度改善

ユーザーが実際のGmail環境で1回目の実機確認を行い、以下が判明した（実メール本文そのものはリポジトリ・報告書に記載していない。判明した「構造」のみを設計に反映する）。

**分類の見直し**

- えきねっとの「座席番号のご案内」メールは、単独でも列車名・区間・時刻・号車・座席番号を含んでいることが判明した。それまで`対象外`に分類していたが、`予約補完メール`（`RELEVANCE_SUPPLEMENTARY`）という区分を新設し、対象外から切り出した
- `予約補完メール`は、対象(`TARGET`)・判定不能(`UNKNOWN`)と同様にユーザーが個別に解析ボタンを押せる。既存の`extract_ekinet()`をそのまま適用し、複数メールを自動で結合・統合する処理は行わない（1メール＝1候補という設計は維持）
- 複数メール（主メール＋補完メール）を自動的に関連付けて1つの予約として統合する機能は、影響範囲が大きいためPhase Cでは実装せず、Phase D以降の検討課題として記録するに留めた

**えきねっとの時刻抽出**

- 実メールの区間表記が「駅名(○時○分) → 駅名(○時○分)」という、ラベル無しの構造だったため、`(?:出発時刻|発時刻)[:：]?\s*(\d{1,2}:\d{2})`のようなラベル依存の正規表現では出発/到着時刻を取得できていなかった
- `_STATION_TIME_ROUTE_RE`という新しい正規表現を追加し、「駅名(○時○分) → 駅名(○時○分)」という構造そのものから、駅名・時刻をハードコードせずに抽出できるようにした。ラベル形式で既に取得できている値がある場合はそちらを優先し、上書きしない

**Agodaの日付・ホテル名抽出**

- チェックイン/チェックアウト日は、ラベル（「チェックイン日：」等）の値が同じ行になく、曜日を挟んだ別の行に書かれている構造だった（例：ラベル行→「曜日 YYYY年M月D日」の行→「（時刻情報）」の行）。ラベルと同じ行だけを見る実装だったため取得できていなかった
- ラベルの直後（既定80文字以内）から日付パターン（`YYYY年M月D日`、区切り文字前後のスペース・全角スペースを許容）だけを探す方式（`_find_date_near_label`）に変更し、曜日等の前置き文字があっても日付を取得できるようにした
- ホテル名は、明示的なラベル（「ホテル名：」等）が本文に存在しない可能性が高いことが分かった。ラベル候補を拡張し、ラベルが見つかった場合は同じ行または直後の非空行を値として採用する方式（`_search_label_value`）にしたが、**ラベル自体が本文に無い場合は依然としてNoneのまま**（見出しタグ等のHTML構造から推測する処理は、誤抽出のリスクが高いため今回は実装していない。14.7既知の制限に追記）
- HTML→textの変換では、`&nbsp;`・全角スペースを通常の半角スペースへ正規化する処理を追加した（`html_to_text`）

**confidence判定**

- 14.4節のとおり、「予約として重要な項目」の充足度を基準にする方式へ変更した（`高`／`中`／`低`の3段階）

**今回の改善で解決していない可能性がある点（次回実機確認で要確認）**

- ホテル名にラベルが本当に存在しないのか、見出しタグ等で何らかの目印があるのかは未確認
- チェックイン/チェックアウトのラベルが2回以上出現する構造（例：ヘッダー行とデータ行で「チェックイン」の語が重複する等）がある場合、80文字の探索範囲内で誤った日付を拾う可能性がある
- Agodaの日付・時刻表記が英語表記になるケースは未検証

### 14.9 Phase C実機再確認（えきねっと2回目）を踏まえた座席番号抽出改善

ユーザーが14.8の改善を実際のGmail環境で再確認したところ、出発/到着時刻・分類（対象外→予約補完メール）はいずれも改善が確認できた。一方、「座席番号のご案内」メールで、号車（例：8号車）は取得できるが座席番号（例：19番A席）が取得できないことが判明した。

**原因**：号車は`(\d+)[ \t]*号車`という構造ベースの正規表現で取得できていたが、座席番号は`(?:座席番号|座席)[:：]?\s*(...)`という**ラベル依存**の正規表現しか用意していなかった。実メールの座席情報は「8号車 19番A席」のようにラベルを伴わず、号車の直後に続く構造だったため、座席番号側だけが取得できていなかった。

**変更内容**：

- `_CAR_SEAT_COMBINED_RE`という新しい正規表現を追加し、「N号車 M番X席」（Nは号車番号、Mは座席番号、Xは座席アルファベット）という構造そのものから、号車・座席番号をハードコードせずに抽出できるようにした
- ラベル形式（「座席番号：」等）で既に座席番号が取得できている場合は、そちらを優先し、構造パターンによる値で上書きしない
- 号車・座席番号の数字は1桁・2桁以上どちらも許容し、号車と座席情報の間の空白（全角/半角スペース、HTML→text変換由来の改行）も許容する
- 乗車日については、座席番号案内メールに日付の記載（「乗車日：」等のラベル）が無い場合、件名等から推測して補完する処理は追加していない（引き続きNoneのまま）。将来、主メール（申込完了メール）と補完メールを列車名・区間・時刻・予約識別情報等で関連付ける設計に拡張する際、主メール側の乗車日を利用する想定（14.8の複数メール統合方針を維持）

### 14.10 Phase C実機再確認（Agoda3回目）を踏まえたホテル名抽出改善

ユーザーが14.8の改善を実際のGmail環境で再確認したところ、チェックイン日・チェックアウト日・料金・予約/申込識別情報はいずれも取得成功しconfidenceも「高」になったが、**ホテル名のみ解析結果に表示されなかった**。ユーザーからは、TripFlowの候補一覧（解析前のメール表示）に「予約確認 [英語ホテル名] [日本語ホテル名]」という構造でホテル名が存在していることを目視確認したとの報告があった。

**テキスト経路の確認**：候補一覧（解析前）に表示される文字列は、件名（`candidate.subject`）とGmail生成のsnippet（`candidate.snippet`、Phase Bで`format=metadata`取得時に得る短い抜粋）であり、いずれも本文全文ではない。一方、解析ボタン押下時にAgoda parserへ渡される本文（`body_text`）は、`fetch_message_body()`が`format=full`で取得したtext/plain（無ければtext/htmlをテキスト化したもの）であり、件名・snippetとは別の経路である。つまり、ユーザーが目視したホテル名が件名・snippet由来なのか、本文にも同じ構造で存在するのかは、実メールを直接確認できないため断定できない。この不確実性に対応するため、後述のとおり件名・本文・snippetの3つすべてを試す設計にした。

**変更内容**：

- 新しいホテル名抽出手段として、「予約確認」等の見出し語（分類ロジックのAgoda対象キーワードと同じものを流用。特定のホテル名・件名文言はハードコードしていない）の直後に続くテキストをホテル名候補として取り出す仕組み（`_extract_hotel_name_after_anchor`）を追加した
- 信頼度の高い順に、(1) 明示的なラベル（「ホテル名：」等）、(2) 件名中の見出し語の直後、(3) 本文中の見出し語の直後、(4) Gmail snippet中の見出し語の直後、を試す（`_extract_agoda_hotel_name`）。件名は1行で完結しており誤抽出のリスクが低いため、本文より先に試す
- 英語ホテル名・日本語ホテル名が連続して存在するケースは、区切り方法を確定的に判断できないため、言語ごとに分割はせず「見出し語の直後、同じ行の範囲」をまとめて1つの値として扱う
- 誤抽出防止として、見出し語の直後に続くテキストが (a) 80文字を超える、(b) 句点・感嘆符・「ありがとう」「様」「円」「チェックイン」等、文章や他項目のラベルらしき語を含む、(c) 改行をまたいでいる、のいずれかに該当する場合はホテル名として採用せずNoneを維持する（`_is_plausible_hotel_name`）
- 見出し語・既存ラベルとも、直後に区切り文字（コロン・空白・改行・文字列終端）が続く場合のみ採用するよう修正した。修正前は「ホテル名」というラベル文字列が、値であるホテル名自体の一部（例：「…ホテル名古屋…」）に偶然一致し、誤った値を切り出す不具合があった（テストで発見し修正。回帰テストを追加）
- レビュー依頼・広告メール等は、見出し語が本文に存在しない限りホテル名候補が生成されないため、既存の分類ロジック（対象／予約補完メール／対象外／判定不能）との整合性は維持されている。対象外(EXCLUDED)は`can_analyze()`により解析自体が行われない

**今回の改善で解決していない可能性がある点（次回実機確認で要確認）**：

- ホテル名が件名・snippetにのみ存在し本文には無い場合、あるいはその逆の場合の両方に対応したつもりだが、実際にどの経路で取得できたかは実機確認でのみ確認できる
- 英語名＋日本語名を1つの値としてまとめて表示する仕様が、実際の表示として適切か（日本語名だけを表示したい場合は別途分割ロジックの検討が必要）
- 見出し語がAgoda公式の実際の件名文言と完全に一致しているかは未確定（ユーザー報告の「予約確認」という語がそのまま実際の文言だったことは確認できたが、他の言い回しのバリエーションがある可能性は残る）

### 14.11 Phase C実機再確認（Agoda4回目）を踏まえた「見出し語自体の誤抽出」修正

14.10の改善を実際のGmail環境で再確認したところ、チェックイン日・チェックアウト日・料金・予約/申込識別情報はいずれも取得成功しconfidenceも「高」になったが、**ホテル名欄に見出し語そのもの（「予約確認」）が誤って表示された**。

**原因の特定（コード解析による。実メール本文は確認していない）**：`_extract_hotel_name_after_anchor()`は、見出し語（「予約確認」等）を見つけたら、その直後（空白・改行を読み飛ばした先）にある1つのまとまりをホテル名候補として返す実装だった。このとき、直後のまとまりが「見出し語そのもの」であるケースを想定していなかった。

具体的には、次のような構造（架空データで再現）で発生することをコード上で確認した。

```
予約確認

予約確認

Sample Hotel Tokyo サンプルホテル東京
```

このように見出し語が2箇所（例：バナー見出しと本文セクション見出し）に続けて現れ、間が空行のみの場合、1つ目の「予約確認」の直後の空白・改行をすべて読み飛ばした結果、2つ目の「予約確認」自体がホテル名候補として抽出され、それが`_is_plausible_hotel_name()`のどのチェック（長さ・禁止語）にも該当しなかったため、そのまま採用されてしまっていた。

**どの経路（ラベル／件名／本文／snippet）で発生したかについて**：`_search_label_value()`が使うラベル一覧（「ホテル名」等）には「予約確認」は含まれておらず、ラベル方式で発生した可能性は低い。件名は通常1行で完結しており、件名自体に「予約確認」が2回含まれる可能性は低い。Gmail snippetも通常は連続したプレビュー文字列であり、見出し語が空行を挟んで2回現れる構造にはなりにくい。消去法として、**本文（`fetch_message_body()`で取得しhtml_to_text()でテキスト化したもの）の中で、見出し語がバナー等で2回連続して現れた可能性が最も高い**と判断したが、実メール本文を直接確認していないため断定はできない。

**変更内容**：

- `_is_plausible_hotel_name()`に、切り出した値が見出し語（`_AGODA_HOTEL_NAME_ANCHORS`のいずれか）自体と完全一致する場合は却下する判定を追加した。大文字小文字を無視して比較する（英語見出し語向け）
- `_extract_hotel_name_after_anchor()`を、見出し語の最初の出現だけでなく、同じ見出し語の2回目以降の出現（上限5回）も順に試すように変更した。これにより、1回目の直後が見出し語自体で却下された場合でも、2回目の見出し語の直後にある実際のホテル名を取得できる
- 英語見出し語（Confirmation等）の照合を大文字小文字を無視するように変更した（実メールでの表記揺れに備えるため）
- 見出し語をすべて試しても妥当な値が見つからない場合は、引き続き`None`を返す（安全側の設計を維持）

**誤抽出防止策のまとめ**：ホテル名候補は、(1) 見出し語自体と完全一致しない、(2) 80文字を超えない、(3) 句点・挨拶語・他項目のラベルらしき語を含まない、(4) 改行をまたがない、をすべて満たす場合のみ採用する。1つでも満たさない場合は、その見出し語の別の出現・別の見出し語・別の情報源（件名／本文／snippet）を順に試し、最終的にすべて満たさなければ`None`のまま返す。

## 15. Web v0.4 Phase Dの実装内容（前半：スマートEX・スカイマークの土台作り）

Phase Cで、えきねっと・Agodaの検索・分類・予約情報抽出・登録候補プレビューが実機確認済みとなった（GitHubへcommit・push済み）ことを受け、Phase Dでは対応サービスをスマートEX（🚅）・スカイマーク（✈️）へ拡張する。

**重要**：スマートEX・スカイマークの実際のメール件名・本文は、Phase D前半の時点では一度も確認していない。そのため今回は、検索・分類・表示の土台を整えるところまでとし、実機確認前に抽出ロジックを強引に作り込むことはしていない（13章「実メール確認」と同じ方針）。

### 15.1 サービス識別子の設計方針

新サービスの内部識別子は、`smart_ex`・`skymark`のようなsnake_caseを新設するのではなく、既存の`RESERVATION_SERVICE_OPTIONS`（`web/components.py`、手動予約登録フォームで既に「スマートEX」「スカイマーク」を選択肢として持っていた）と同じ表示名文字列（`"スマートEX"`・`"スカイマーク"`）をそのまま`service`として使うことにした。えきねっと・Agodaも同様に表示名を直接`service`の値として使っており（`"えきねっと"`・`"Agoda"`）、この既存パターンに合わせることで、表示名⇔内部識別子の変換層を新設せずに済む。

### 15.2 Gmail検索

`web/gmail_service.py`の`SERVICE_SEARCH_RULES`に、スマートEX・スカイマークを追加した。

- スマートEX：`from_domains=["smart-ex.jp"]`、`subject_keywords=["スマートEX", "SmartEX"]`
- スカイマーク：`from_domains=["skymark.co.jp", "skymark.jp"]`、`subject_keywords=["スカイマーク", "Skymark"]`

ドメインは各社が公表している公式サイトのドメインを初期案として設定した（個人情報ではなく、各社が一般公開している情報）。実際の送信元メールアドレスをユーザーのGmailで確認したものではないため、えきねっと・Agodaと同様、実機確認の結果を踏まえて見直す前提。検索期間の指定方法（`months`引数、UIの「直近◯か月」選択）はPhase Bから変更していない。

`SUPPORTED_SERVICES`は`SERVICE_SEARCH_RULES`のキーから自動的に導出されるため、コード変更はこの1箇所のみで4サービスに対応した。

### 15.3 メール分類

`web/reservation_parser.py`の`SUBJECT_CLASSIFICATION_RULES`に、スマートEX・スカイマークを追加した。ただし、実際の予約確認メールの件名文言を確認していないため、**対象(TARGET)ルールはまだ設定していない**。

- 対象外(EXCLUDED)キーワードのみ設定：「レビュー」「アンケート」「キャンペーン」「広告」「セール」「お知らせ」。これらはユーザーから「広告・キャンペーン・お知らせ・レビュー等を予約情報として誤認しないように」と明示的に指示された一般的なマーケティングメール用語であり、特定の実件名を推測したものではない
- 上記のいずれにも一致しない件名は、すべて判定不能(UNKNOWN)となる。分類の考え方（対象／予約補完メール／対象外／判定不能の4区分）自体はPhase Cから変更していない
- `classify_candidate()`・`can_analyze()`のロジック本体はサービス名に依存しない汎用実装のため、コード変更は不要だった（`SUBJECT_CLASSIFICATION_RULES`にエントリを追加しただけ）

判定不能に分類されたメールも、ユーザーが「🔍 予約情報を解析」ボタンを押せば個別に解析できる（Phase Cから変更していない挙動）。実機確認でスマートEX・スカイマークの実際の予約確認メールの件名パターンが分かり次第、対象(TARGET)ルールを追加する。

### 15.4 予約情報抽出（土台実装）

`web/reservation_parser.py`に`extract_smart_ex()`・`extract_skymark()`を追加した。実メールの構造が未確認のため、いずれも「ラベル：値」形式の汎用的な抽出のみを行う。

- スマートEX：乗車日・出発駅・到着駅・列車名・出発/到着時刻・号車・座席番号・予約/申込番号（えきねっとと同じ項目名のラベルで探索）
- スカイマーク：搭乗日・出発空港・到着空港・便名・出発/到着時刻・予約/申込番号

えきねっと側で実機確認により発見した**構造依存**の抽出（「駅名(○時○分) → 駅名(○時○分)」・「N号車 M番X席」）は、スマートEX（JR東海等が運営する別サービスで、メールテンプレートが同一とは限らない）へは流用していない。一方、「N号車」の抽出（`(\d+)[ \t]*号車`）は日本語の助数詞としての一般的な表記パターンであり、特定サービスの実メール構造から発見したものではないため、スマートEXでも共通で使用している。

既存の`extract_ekinet()`・`extract_agoda()`は、この対応にあたって一切変更していない（Phase Cで実機確認済みの動作を壊さないため）。

confidence判定は既存の`_confidence_from_core()`をそのまま再利用し、「予約として重要な項目」基準の考え方を維持している。

- スマートEX：乗車日・区間（出発駅+到着駅）・列車名・出発/到着時刻の4項目
- スカイマーク：搭乗日・区間（出発空港+到着空港）・便名・出発/到着時刻の4項目

実メール未確認の段階では大半のメールで抽出項目が少なく、confidenceは「低」または「中」にとどまる見込みである。これは意図した挙動であり、情報が不足しているのに「高」と誤判定することはない。

### 15.5 登録候補データ構造の拡張

## 17. Web v0.4 Phase D実機再確認（スマートEX2回目）を踏まえた区間抽出改善

16章の改善を実際のGmail環境で再確認したところ、乗車日・列車名・号車・座席番号・予約/申込識別情報はいずれも取得成功しconfidenceは「中」になったが、出発駅・到着駅・出発時刻・到着時刻が引き続き未取得だった。

## 18. Web v0.4 Phase D実機再確認（スマートEX3回目）を踏まえた原因調査と修正

17章の改善（3区間構造対応）を実際のGmail環境で再確認したところ、TARGET分類・乗車日・列車名・号車・座席番号・予約/申込識別情報はいずれも成功し（confidence「中」）、TARGET分類の成功は確認できた。一方、出発駅・到着駅・出発時刻・到着時刻は引き続き未取得だった。ユーザーからは、候補メール表示上に区間情報（「駅名(時刻)→列車名→駅名(時刻)」に相当する内容）が連続して存在することを目視確認済みとの報告があり、「実メールを想像した新しい正規表現の追加ではなく、まずコード経路から原因を特定すること」という指示を受けた。

### 18.1 調査したコード経路

`fetch_message_body()`（Gmail API、`format=full`）→ `_collect_body_parts()`（MIME再帰走査・base64urlデコード）→ `resolve_body_text()`（text/plain優先、無ければ`html_to_text()`）→ `extract_smart_ex()`（区間正規表現）という経路を確認した。`html_to_text()`は、スクリプト/スタイル除去→ブロック要素の改行変換→残りタグの空白置換→実体参照デコード→連続空白・NBSP・全角スペースの正規化→3行以上の空行圧縮、という順で処理する（`web/reservation_parser.py`、変更なし）。

候補一覧の解析ボタン押下時にparserへ渡されるのは、常に`subject`（件名）と、この経路で得られた`body_text`（本文）である。候補一覧の表示（解析前）に使われるテキスト（`snippet`）とは別経路であり、ホテル名抽出（14.10章）で確認済みの整理のとおり。

### 18.2 原因調査の方法と結果

実メール本文には一切アクセスできないため、**「確認済みの構造情報（駅名(時刻)→列車名→駅名(時刻)という並び）を変えずに、時刻表記や記号だけを変えた複数の架空データ」を使い、`_SMART_EX_STATION_TRAIN_STATION_RE`が一致するかどうかを機械的に検証した**。個人情報を含む実データは一切使用していない。

検証したパターンと結果：

| 変更点 | 一致 |
|---|---|
| 時刻表記が「○時○分」（当初の想定） | 一致した |
| 全角数字＋「○時○分」 | 一致した（Pythonの`\d`が全角数字にも対応するため） |
| 時刻表記が「○:○」（コロン区切り） | **一致しなかった** |
| 矢印が「➡」「⇒」等の別Unicode文字 | 一致しなかった |
| 括弧がASCII以外（【】等） | 一致しなかった |
| 時刻の位置が駅名より前 | 一致しなかった |

このうち「○:○」（コロン区切り時刻）は、このモジュール内の他のラベルベース時刻抽出（`(?:出発時刻|発時刻)[:：]?\s*(\d{1,2}:\d{2})`）で既に採用している一般的な時刻表記であり、実メールからの新たな推測ではなく、既存の許容範囲の延長といえる。矢印の種類・括弧の種類・語順については、これを支持する具体的な根拠（ユーザーからの構造確認）が無いため、今回は対応を見送った。

**結論**：時刻表記が「○:○」であった場合に一致しないことをコード上で確認できたため、これを最も可能性の高い原因と判断した。ただし、実メール本文を直接確認したわけではないため、100%の確証ではない。次回の実機確認で解消しない場合は、矢印の種類・括弧の種類等、他の要因を検討する必要がある。

### 18.3 変更内容（区間抽出）

- 時刻部分のサブパターンを`_SMART_EX_TIME_TOKEN_RE`として切り出し、「○時○分」「○:○」（全角コロンを含む）のどちらにも一致するようにした
- 一致した生の時刻表記は`_parse_smart_ex_time_token()`でHH:MM形式に変換する
- スマートEX専用の直接隣接構造（`_SMART_EX_STATION_TIME_ROUTE_RE`、コロン時刻対応）を新設した
- `_SMART_EX_STATION_TRAIN_STATION_RE`（3区間構造）も、この共通の時刻サブパターンを使うように変更した
- 抽出の優先順位は、(1) えきねっとと共用の「○時○分」限定・直接隣接構造 → (2) スマートEX専用・コロン時刻対応の直接隣接構造 → (3) スマートEX専用・コロン時刻対応の3区間構造、の順とした。既存の直接隣接パターンの考え方は維持しつつ、実際のnormalize結果（時刻表記の揺れ）に合わせて一般化している
- えきねっとと共用の`_STATION_TIME_ROUTE_RE`自体は変更していない（えきねっとの実機確認済み動作を壊さないため）

### 18.4 テスト作成中に発見した別の不具合（列車名が矢印を取り込む）

3区間構造のテストを架空データで作成する過程で、列車名抽出の既存フォールバック正規表現（`[^\s\n]*?(?:のぞみ|...)...号`）が、列車名の直前に矢印が空白無しで隣接する場合（「→のぞみ99号」等）に**矢印自体を列車名の一部として取り込んでしまう**不具合を発見した。原因は、正規表現の「列車名の前に許容する文字」の文字クラスに矢印（→）が含まれていたため。スマートEX専用の当該正規表現の文字クラスから矢印を除外し、矢印を取り込まないよう修正した。えきねっとの同種の正規表現（同じ構造だが独立したコピー）は変更していない。

### 18.5 料金が表示されなかった原因の調査

ユーザーからの「1. amount抽出に失敗している／2. amountがNoneになっている／3. UI条件分岐の問題／4. 実行中コードと修正コードが一致していない」という問いに対し、コードを確認した。

- UIの条件分岐（`if candidate.amount is not None: st.markdown(...)`）は、前回追加したとおり正しく存在していることを確認した（3. は該当しない）
- `extract_smart_ex()`の`amount_raw`抽出は、「運賃」「料金」「合計金額」「合計料金」「お支払い金額」というラベルへの一致を前提にしており、これらのラベルは実メールでの確認を経ていない**初期案のまま**だった
- 今回の実機確認でも料金が取得できていないことから、実際の運賃表示に、これらのラベルのいずれとも一致しない文言（またはラベル自体が無い、値のみの表示）が使われている可能性が高いと判断した（1. amount抽出に失敗している、に該当する可能性が高い）

**対応**：実際のラベル文言を確認しないまま新しいラベル候補を追加すると、今回の区間・列車名の教訓と同様に「推測だけで正規表現を追加する」ことになってしまうため、**今回はamount抽出ロジックを変更していない**。次回の実機確認で、実際のラベル文言（またはラベルの有無）を確認いただく前提とした（詳細は本報告書「次に実機確認すべき内容」参照）。

### 18.6 乗車用ICカード指定内容メールの分類方針

ユーザーから、スマートEXには「乗車用ICカード指定内容」という別メールが存在し、乗車用ICカードに関する情報を含むことが実機確認できたとの報告があった。これは、えきねっと13.3節・14.8節で扱った「座席番号のご案内」（予約本体を補完する別メール）と同じ位置づけと考えられる。

新しいクラス（`RESERVATION_SUPPLEMENT`等）を新設するのではなく、**既存の`RELEVANCE_SUPPLEMENTARY`（予約補完メール）をそのまま再利用**して分類できると判断した。`SUBJECT_CLASSIFICATION_RULES`のスマートEXに、「乗車用ICカード指定内容」を件名キーワードとする`RELEVANCE_SUPPLEMENTARY`ルールを、対象外・対象ルールより先に追加した。

`extract_smart_ex()`自体は分類結果（`relevance`）によって抽出ロジックを分岐させていないため、ICカード指定内容メールを解析しても、そのメールに実際に含まれる情報（乗車日・区間等があれば）だけが抽出され、無ければ大半がNoneになるだけでクラッシュはしない。**複数メールの自動統合・DBへの保存処理は、今回も実装していない**（分類ルールの追加のみ）。

### 18.7 既存サービスへの影響

`extract_ekinet()`・`extract_agoda()`・`extract_skymark()`は変更していない。えきねっとと共用の`_STATION_TIME_ROUTE_RE`、えきねっとの列車名抽出正規表現も変更していない。

## 19. Web v0.4 Phase D実機再確認（スマートEX4回目）を踏まえた料金抽出改善

18章の改善（時刻表記の一般化、列車名の矢印混入修正）を実際のGmail環境で再確認したところ、区間（出発駅・到着駅・出発時刻・到着時刻）・乗車日・列車名・号車・座席番号・予約/申込識別情報のすべてが取得成功し、confidenceも「高」になった。「乗車用ICカード指定内容」メールが予約補完メールとして分類されることも確認できた。**料金のみ**、解析カードに表示されなかった。

### 19.1 原因

ユーザーからの実機確認により、実際のスマートEXの予約メールでは、料金情報がラベル形式（「料金：」等）ではなく、**「領収額は、合計XXXX円です。」という文章の中に埋め込まれている**ことが判明した。既存の`amount_raw`抽出は、「運賃」「料金」「合計金額」「合計料金」「お支払い金額」というラベルに`[:：]?\s*`（コロン＋空白）が直接続く形式を前提にしており、文章形式には対応していなかった。

### 19.2 変更内容

`extract_smart_ex()`の`amount_raw`抽出に、以下のパターンを追加した（既存のラベル形式パターンはそのまま維持し、優先的に試す）。

```
領収額[^\n]{0,10}合計[ \t　]*([0-9][0-9,]*)[ \t　]*円
```

「領収額」と「合計」という2つの語が近接して現れ、その直後に金額＋「円」が続く、という構造そのものをパターン化した。間にある助詞・読点（「は、」等）は固定文言としてハードコードせず、10文字以内の任意の文字として許容している。カンマの有無、「合計」と金額の間の全角/半角スペースの有無にも対応する。

### 19.3 誤検出防止策

「領収額」「合計」の**両方**が近接して現れない限り一致しないため、本文中の無関係な数字（会員番号・予約番号・列車番号・日付・時刻・ICカード番号等）を誤って金額として取得するリスクは低いと判断した。テストでは、以下を確認している。

- 「領収額」「合計」のどちらか一方だけが本文にあり、もう一方が近くに無い場合は取得しない
- 会員番号・予約番号・列車番号・乗車日・出発時刻・ICカード番号のみを含む本文からは、amountがNoneのままであることを確認した

### 19.4 既存サービスへの影響

`extract_ekinet()`・`extract_agoda()`・`extract_skymark()`は変更していない。Agodaの金額抽出ロジック・ラベルは変更していない。既存のスマートEXラベル形式（「運賃：」等）による金額抽出も、優先順位を維持したまま動作する。
